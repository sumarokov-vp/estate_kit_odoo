# User Onboarding — Настройка нового пользователя

Процесс добавления нового сотрудника (менеджера, агента) с доступом к объектам
недвижимости и/или CRM-воронке.

> **Важно:** последний шаг — **перезапуск Odoo** — обязателен, если права
> назначались не через стандартный UI, а через ORM-shell или SQL. Без него
> живые воркеры держат устаревший кэш членства в группах, и пользователь видит
> пустые списки, сколько бы раз ни перезаходил. См. раздел [«Перезапуск
> сервера»](#5-перезапуск-сервера-обязательно).

---

## Обзор: три независимых слоя доступа

Чтобы новый пользователь реально что-то увидел, должны совпасть **все** слои:

| Слой | Что даёт | Где настраивается |
|------|----------|-------------------|
| 1. Роль (группы) | ACL на модель + record rules (видимость записей) | Settings → Users → секция Estate Kit / Sales |
| 2. Членство в команде | Непустая воронка CRM (Pipeline) | CRM → Конфигурация → Отделы продаж → Участники |
| 3. Свежий кэш | Применение прав работающими воркерами | Перезапуск Odoo |

Пропуск любого слоя = пользователь видит ноль записей.

---

## 1. Создание пользователя

**Settings → Users & Companies → Users → New.**

- Имя, email (логин), компания.
- Роль: **Пользователь** (не Администратор для рядовых сотрудников).

## 2. Назначение ролей (привилегий)

В форме пользователя, секция **Estate Kit** и **Продажи**:

- **Листинг** / **Маркетинг** — доступ к объектам недвижимости и размещениям
  (см. [система прав](../../../.claude/skills/permissions/SKILL.md) — справочник
  привилегий Estate Kit).
- **Продажи (Sales)** — доступ к CRM-заявкам:
  - **User: Own Documents Only** — видит только заявки, где он продавец.
  - **User: All Documents** — видит все заявки агентства.

> **Назначать роли только через UI** (dropdown в форме пользователя). Интерфейс
> корректно раскручивает `implied_ids` — например, «All Documents» автоматически
> подтягивает «Own Documents Only», которая держит ACL на `crm.lead`.
>
> **Не назначать группы напрямую через таблицу `res_groups_users_rel` или через
> `res.groups.write({'user_ids': ...})`** — эти пути НЕ раскручивают
> `implied_ids`, и пользователь останется без ACL (увидит пустой экран или
> ошибку доступа). Если по какой-то причине правишь из shell — только через
> `env['res.users'].browse(uid).write({'group_ids': [(4, gid)]})`.
>
> Поля Odoo 19: `res.users.group_ids`, `res.groups.user_ids` (старые
> `groups_id` / `users` переименованы).

## 3. Членство в команде продаж (для CRM)

Чтобы воронка (Pipeline) не была пустой, пользователь должен быть **участником
команды продаж**:

**CRM → Конфигурация → Отделы продаж → (команда) → вкладка «Участники» → добавить.**

Без членства Odoo показывает воронку «первой команды» с подсказкой *«вы не
являетесь членом отдела продаж»* — пустую.

Из shell (если нужно): `env['crm.team.member'].create({'crm_team_id': <team>, 'user_id': <uid>})`.

## 4. Дефолтный фильтр воронки

Воронка по умолчанию применяет фильтр **«Моя воронка»** (показывает только
заявки, где пользователь — продавец). Менеджеру, который должен видеть всё, это
мешает.

В этой инсталляции фильтр **снят** на уровне действия воронки
(`crm.crm_lead_action_pipeline`, убран `search_default_assigned_to_me`).
Закрепление в модуле — см. задачу `todos/008-crm-pipeline-default-filter.yaml`.
Если фильтр вернулся после апгрейда — он снова появится как чип «Моя воронка»,
его можно снять крестиком вручную.

## 5. Перезапуск сервера (обязательно)

Если хоть один из шагов 2–3 выполнялся **через ORM-shell или SQL** (в обход UI),
обязательно перезапустить Odoo — иначе работающие воркеры применяют старый кэш
прав, и пользователь не увидит данные даже после перезахода:

```bash
ssh royal_estate_odoo "docker restart odoo-odoo-1"
```

Дождаться готовности:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://royalestate.smartist.dev/web/login   # ждём 200
```

> Назначение прав **через UI** (Settings → Users) перезапуска не требует — Odoo
> сам шлёт registry signal. Перезапуск нужен именно для изменений в обход
> интерфейса.

## 6. Проверка

- Пользователь заходит, открывает нужный раздел — записи на месте.
- Для воронки CRM: если стоит чип «Моя воронка» и заявки чужие — снять фильтр.
- Диагностика из shell (имитация доступа от имени пользователя):

  ```python
  print(env['crm.lead'].with_user(<uid>).search_count([]))
  ```

  Если shell показывает N, а реальная сессия в браузере — 0, это устаревший кэш
  воркеров → см. шаг 5.
